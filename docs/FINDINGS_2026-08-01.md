## 1. CONFIRMED issues found in THIS pass (live code verified)

These are real, reproducible in the current tree, and worth action. Everything else in the audits is either already fixed or staged.

### 1.1 🔴 `api-handler.ts` — domain errors matched by **string class name**, not `instanceof`

**File:** `web/src/lib/api-handler.ts:45-56`

```ts
if (domainErr.name === 'RentalBookError') { ... }
if (domainErr.name === 'KycStateError' || domainErr.name === 'GuarantorStateError' || ...) { ... }
```

**Why it's a real bug:** bundlers/minifiers (and `esbuild` for the worker bundle at `worker:build`) can mangle class names in production. A production build that minifies class names turns `KycStateError` into `e`/`t`, the `.name === '...'` check silently fails, and the request falls through to the generic 500 handler — losing the correct HTTP status + error code. This is exactly the class of bug that surfaces only in prod.
**Recommendation:** replace string matching with `instanceof` against the typed error classes (`lib/api-error.ts` already defines `ApiError`, `NotFoundError`, `ValidationError`, etc.), or give each error a stable `code` string matched on that. Add a unit test that would fail under name mangling. **Effort: ~0.5 day. Priority: high (it's in the hot path of every mutating route).**

### 1.2 🟡 Device routes — inconsistent production/staging guard

**Files:** `web/src/app/api/device/data/route.ts:12` vs `.../device/permissions/route.ts:12-16`

- `device/data/route.ts` trusts the request body when `TEST_MODE==='true' || NODE_ENV==='development'` and has a separate `isProdOrStaging` check (lines 13-15) — **asymmetric**.
- `device/permissions/route.ts` uses a simpler `if (TEST_MODE || NODE_ENV==='development')` with **no explicit staging exclusion**.

**Why it matters:** the public-beta threat model treats **staging** as production-adjacent. If these two sibling routes disagree on whether staging allows body-derived rider identity, you have a data-injection gap on exactly one of them. (This is Ticket #55's intent; only partially closed — one route got the `APP_ENV==='staging'` guard, the other may not.)
**Recommendation:** extract a shared `assertDeviceSeedAllowed(env)` helper used by both routes so the policy is identical by construction; add a regression test asserting both routes reject body-identity when `APP_ENV === 'staging'`. **Effort: ~0.5 day.**

### 1.3 🟡 Admin web — monolith screens re-accumulated (architecture regression)

**Evidence (live):** `RiderManagement.tsx` = **2455 lines / 108.6 KB**; `RiderDetailDialog.tsx` = 62 KB; `TransactionManagement.tsx` = 50 KB; `TicketManagement.tsx` = 48.9 KB; `KycManagement.tsx` = 48 KB. The 2026-08-01 split attempts were **reverted** (`ee60417`, `02facf1`) for breaking tests.
**Why it matters:** these are past the point where a single PR can safely review them; every future edit compounds risk and the "split later" debt grows with each feature.
**Recommendation:** re-attempt the RiderManagement split with **"tests stay green" as the merge gate**, broken into 4 sub-PRs (Filters → Row → Modals → Shell-router). Also confirm whether the 274-component console is shipped as a single client bundle (only 3 `page.tsx` under `app/admin/`) and code-split the 9 heavy screens with dynamic `import()`. **Effort: 2–4 weeks (ticket #21).**

### 1.4 🟡 Design system — `AppTypography` centrally bypassed after R2.1

**Evidence (live grep):** `AppTypography.` refs **122 → 57**; raw `GoogleFonts.` calls **69 → 85**. After the R2.1 alias cleanup removed `button`/`input`/etc., screens now reach straight for `GoogleFonts` instead of the design system.
**Why it matters:** it's the classic over-strict-centralization failure — the 19-tier scale starved a few legitimate needs, so callers routed around it.
**Recommendation:** identify the 85 `GoogleFonts.` call-sites, find the missing tier(s) they wanted, add them to `AppTypography`, and flip the call-sites back. (Also resolves backlog ticket #4 by necessity.) **Effort: 1–2 days.**

### 1.5 🟢 Dead/deprecated worker job still registered

**Evidence:** `notifications.job.ts` is marked DEPRECATED in `PROJECT_OVERVIEW §11.1` ("tombstone per `index.ts:29-33` — will be removed in next cleanup pass") and `notifications-cleanup.job.ts` is listed as "orphan scheduled."
**Why it matters:** dead scheduled work is a silent-failure and on-call-noise vector.
**Recommendation:** delete both in a single cleanup PR. **Effort: ~30 min.**
