# Voltium Rider App — Implementation Plan (2026-08-21)

**Scope:** Flutter rider app only. Web/infra follow their own plans.
**Method:** Sized to ship as **5 focused PRs**, each ≤ 2 days of work and reviewable on a device.
**Companion:** `AUDIT_DELTA_2026-08-21.md` — full evidence for every item here.
**Comprehensive version:** `IMPLEMENTATION_PLAN_FULL_2026-08-21.md` — adds the deferred items (permissions reconcile, finalize provider migration, top-up flow state, telemetry consolidation, FCM secret audit, full DI refactor) in 3 tiers.
**Audience:** You (device QA) + reviewers. Everything below frames changes as **what a rider sees**, not as diff metrics.

---

## How to read this plan

Each PR has:
- **What the rider sees** — the user-visible before/after.
- **Why now** — concrete risk if we don't.
- **Files touched** — so a reviewer can scan the surface.
- **Acceptance criteria** — exact things to verify on device + in CI.
- **Out of scope** — what this PR is *not* doing (avoids scope creep).
- **Risk** — what could regress.

PRs are ordered by **risk-weighted priority**: correctness first, then compliance, then cleanup.

## PR-1 — Fix `isNewRider` defaulting to `false`

**What the rider sees:** A new rider (first-time OTP) whose backend response is missing or malformed for the `isNewRider` field is now sent to the KYC / onboarding flow instead of straight to the pre-dashboard. **Zero visible change** for the happy path.

**Why now:** This is the **only remaining high-severity correctness bug** from the 2026-07-08 audit. If a future server schema change drops the field, every brand-new rider lands on an empty pre-dashboard with no KYC prompt — bypass risk.

**Files touched:**
- `lib/features/auth/data/repository_impl.dart` (line 56: change `?? false` → `?? true` and adjust the branch)
- `lib/features/auth/domain/entity.dart` (line 26: change default of `isNewRider` from `false` to `true`)
- `lib/models/rider_model.dart` (line 268, 739, 865: change default to `true` in three places — model, JSON parse, cache hydrate)

**Acceptance criteria:**
- [ ] Unit test: `AuthRepositoryImpl.verifyOtp` with a response that omits `isNewRider` returns `VerifyOtpResult(isNewRider: true)` and `nextState` is `Onboarding(KycSubmit)`, not `PreDashboard`.
- [ ] Device: complete fresh signup, observe KYC preflight appears. No regression on returning-rider login.
- [ ] CI: `npm run test:unit` (web) green, `flutter test` green, integration test 06 (`full_auth_login`) still passes.

**Out of scope:** Server-side schema validation. (Server should make this field required; raise a separate ticket if you want me to add the server-side guard.)

**Risk:** Tiny. Default flips, but `isNewRider: true` on a returning rider is the safer outcome (they re-do KYC screens briefly rather than see an empty dashboard).

## PR-2 — Drop the dead `provider` package

**What the rider sees:** Nothing. Slightly smaller APK; no behavior change.

**Why now:** `provider: ^6.1.2` is in `pubspec.yaml` but **zero `lib/` files** import `package:provider/...`. Confirmed via `grep -r "import 'package:provider/provider.dart'" lib/`. Every state holder is on `flutter_riverpod` v3. Carrying the dep is dead weight + a future contributor trap.

**Files touched:**
- `pubspec.yaml` (remove `provider: ^6.1.2` line)
- `pubspec.lock` (regenerated by `flutter pub get`)

**Acceptance criteria:**
- [ ] `flutter pub get` succeeds.
- [ ] `flutter analyze` clean.
- [ ] `flutter test` + integration tests pass.
- [ ] `grep -r "import 'package:provider/" lib/` returns nothing.
- [ ] APK size delta reported in PR description (expected: small drop).

**Out of scope:** Removing `AppProvider` shim (that's PR-3). Even with the package gone, `AppProvider` will still compile because it never imported the package — it just used the constructors directly. PR-3 is the cleanup.

**Risk:** Near zero. CI will catch any straggler import.

## PR-3 — Delete the `AppProvider` shim

**What the rider sees:** Nothing. Slightly faster app startup (one fewer `ProviderContainer` per feature at boot).

**Why now:** `lib/core/state/app_provider.dart` (137 lines) is a backward-compat shim that:
1. Constructs a fresh `ProviderContainer` per feature on every `AppProvider()` call (lines 38-82) — leaks in tests that build it per case.
2. Holds duplicate references to providers that are already in the Riverpod container.
3. Is referenced only by `main.dart:176` (one production call site) and test harnesses.

After PR-2, nothing in the lib actually needs this shim — every screen reads providers via `ref.read(provider.notifier)` directly. The shim is a migration leftover.

**Files touched:**
- `lib/core/state/app_provider.dart` (delete)
- `lib/main.dart` (remove the `AppProvider()` instantiation + injection)
- Any test that imports `AppProvider` — switch to `ProviderContainer` setup directly. (`grep -r "AppProvider()" flutter/test` will list them.)
- `lib/core/state/riverpod_providers.dart` (remove the `appProvider` stub at line 47-49 — it throws `UnimplementedError` if anyone uses it)

**Acceptance criteria:**
- [ ] No production code references `AppProvider` after the PR.
- [ ] All test files updated; `flutter test` green.
- [ ] App boots identically; no startup regression.
- [ ] `grep -r "AppProvider" lib/` returns nothing.
- [ ] `grep -r "AppProvider" test/` returns nothing (or only updated mocks).

**Out of scope:** Migrating `EngagementProvider` / `DevicePolicyProvider` / `ConnectivityProvider` default constructors (N3). If you want, that can be a follow-up: those three are still constructed in `AppProvider(...)` defaults; once the shim is gone, the call sites that need them (which is the router + lifecycle hooks) will read them via Riverpod directly anyway.

**Risk:** Medium. Touches the main bootstrap. PR-2 first is recommended because it's a no-op prerequisite.

## PR-4 — Full en+hi translation sweep (hardcoded English → ARB keys, both languages translated)

**What the rider sees:**
- **Before:** A handful of error toasts, dialog titles, and inline error messages show in English even when the rider's device locale is Hindi. The `LANGUAGE-AUDIT (2026-08-16)` sweep covered the highest-visibility surfaces but stopped short.
- **After:** Every user-visible string (error toasts, dialog titles, snackbar messages, validation copy) routes through `AppLocalizations` and renders in the device locale. **Both `app_en.arb` and `app_hi.arb` carry proper translations for every key — no English fallbacks.**

**Why now:** The user reaffirmed (2026-08-21) that the rider app is en+hi only, and that every new ARB key must have a proper Hindi translation — not an English fallback. A partial sweep leaves Hindi riders seeing mixed-language copy, which breaks the product's locale promise.

**Files touched (the loudest offenders first):**
- `lib/features/wallet/presentation/providers/wallet_provider.dart:192` — `lastError: 'Couldn\'t load your transactions. Pull to retry.'` → ARB key `txterrWalletLoadFailed`
- `lib/features/device_compliance/presentation/providers/device_policy_provider.dart` — similar hardcoded error strings
- `lib/features/notifications/presentation/screens/notifications_screen.dart:241` — `'Failed to delete notification'` → ARB key
- `lib/features/dashboard/presentation/providers/engagement_provider.dart` — error strings
- `lib/features/support/presentation/providers/support_provider.dart` — error strings
- `lib/services/fcm_service.dart` — error toasts
- `lib/services/photo_upload_service.dart` — error toasts
- `lib/app/router.dart:395` — `'Your session expired. Please log in again to continue.'` → ARB key
- `lib/widgets/locked_overlay.dart` — locked-screen copy
- `lib/features/profile/presentation/screens/settings_screen.dart`, `earnings_screen.dart` — error toasts
- `lib/features/kyc/presentation/screens/*.dart` — error/success toasts
- `lib/features/auth/presentation/screens/otp_verification_screen.dart` — remaining hardcoded fallbacks (most already routed)
- ~20 more small files (grep result from audit delta)

**ARB additions:** every new key must appear in BOTH `lib/l10n/app_en.arb` AND `lib/l10n/app_hi.arb`. The user explicitly does not want English fallbacks; if a Hindi translation is uncertain, mark it with a `// hi-review:` inline comment in the ARB file pointing to a human translator, but the Hindi entry must still be present (not blank, not a copy of English).

**Acceptance criteria:**
- [ ] `grep -r "Text('[^']*[A-Z][a-z]" lib/features/**/presentation/ lib/services/ lib/app/ lib/widgets/ | grep -v "AppLocalizations"` returns only intentional hardcoded English (brand names, debug labels, brand words like "VOLTIUM").
- [ ] All new ARB keys present in both `app_en.arb` and `app_hi.arb`.
- [ ] No `// TODO: translate` markers; only `// hi-review:` allowed, and those are tracked in the PR description.
- [ ] **Device: set device to Hindi, trigger each of the error paths above, confirm Hindi strings render.** Set to English, confirm English still works.
- [ ] `flutter test` green; integration tests 06, 28 (offline), 31 (error recovery) still pass.
- [ ] `flutter gen-l10n` runs clean (no missing-key warnings).

**Out of scope:** The `app_*.arb` files only contain `en` and `hi`. No 3rd locale. If a new language is ever needed, that's a separate product decision (do not preemptively scaffold).

**Risk:** Low for English (key extraction is mechanical). Medium for Hindi — I am an AI and will provide my best translation, but the user should expect a translator pass to polish idiomatic phrasing. Anything genuinely ambiguous gets the `// hi-review:` comment + a callout in the PR description.

## PR-5 — Dark-mode coverage gap audit

**What the rider sees:**
- **Before:** A handful of widgets that use `AppColors.surface` (the static, light-only constant) instead of `AppColors.of(context).surface` render with the wrong background in dark mode.
- **After:** Every visible surface uses the theme extension. Switching the device to dark mode is consistent across the app.

**Why now:** `AppColors.of(context)` is the canonical accessor and is in widespread use, but a grep will find stragglers that still reference the static `AppColors.X` for tokens that have light/dark variants (`surface`, `onSurface`, `onSurfaceMuted`, `iconBackground`, `surfaceBright`, `surfaceSubtle`, `borderSubtle`).

**Files touched:**
- Audit pass: `grep -rn "AppColors\.\(surface\|onSurface\|onSurfaceMuted\|iconBackground\|surfaceBright\|surfaceSubtle\|borderSubtle\)\b" lib/ --include="*.dart" | grep -v "AppColors\.of"`
- Replace each hit with `AppColors.of(context).X` (or the appropriate theme lookup).
- Likely < 20 widget files; small surgical edits.

**Acceptance criteria:**
- [ ] `flutter analyze` clean.
- [ ] **Device: toggle dark mode in Settings → confirm every screen in the navigation flow (auth, KYC, dashboard, wallet, support, profile) renders correctly.** Especially: dashboard rent-prompt cards, wallet top-up flow, KYC documents, notification cards.
- [ ] No `AppColors.of(context).X` calls were *regressed* (verify the swap didn't move a static-correct value to a wrong context-aware one — both should look right in light mode).

**Out of scope:** Dark-mode design polish (e.g. proper dark variants for the brand gradient). That's a design pass, not an audit fix.

**Risk:** Low. Color-only changes; widget structure is untouched.

## PR-6 (optional) — Delete `VoltiumApiService`, use generated client directly

**What the rider sees:** Nothing. Slightly faster compile times and no more map-of-strings-anywhere in the API layer.

**Why now:** `VoltiumApiService` wraps `VoltiumApiClient` (the generated client) and converts typed responses back to `Map<String, dynamic>` via `response.toJson()`. That throws away the type safety the generated client provides. This is the only structural cleanup I'd add if you have appetite.

**Files touched:**
- `lib/services/voltium_api_service.dart` (delete; route all callers to `VoltiumApiClient` or repository classes directly)
- All callers (`grep -rn "VoltiumApiService" lib/` — likely 10-15 files)
- Test mocks that target `VoltiumApiService` (likely in `test/`)

**Acceptance criteria:**
- [ ] `grep -rn "VoltiumApiService" lib/ test/` returns nothing.
- [ ] `flutter analyze` clean.
- [ ] `flutter test` + integration tests green.

**Risk:** High. Touches many call sites. **Recommend deferring** unless you have a reason (e.g. a real type-safety bug surfaced in QA). The other 5 PRs are higher value.
