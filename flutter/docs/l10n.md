# Localization conventions (Voltium Flutter)

This document is the source of truth for how the rider app's `en`/`hi`
localization files are maintained. It exists because conventions for ARB
edits, casing, and the no-fallback rule have been disputed multiple
times in the past. If you change a convention, update this file in the
same PR.

## Language scope

- The rider app ships **en + hi only**. No 3rd language (Tamil, etc.)
  unless product signs off explicitly.
- Both `app_en.arb` and `app_hi.arb` must carry proper translations.
  English fallbacks for missing Hindi are **not allowed**.
- If a Hindi translation is uncertain, mark the line with `// hi-review:`
  and the human translator will do the bulk pass later. The shipped
  key still goes through CI; the marker is informational.

## ARB hygiene rules

### Casing

For **labels rendered through letter-spacing typography**
(`AppTypography.overline`, `letterSpacing: 1.0+`): the ARB value is
ALL-CAPS ("SECURITY DEPOSIT", "PICKUP PHOTOS"). The renderer
applies the typography; the value already matches it.

For **body text and chip labels**: the ARB value is sentence case
("Security deposit", "Pickup photos"). Do not write "Top Up" in a
body sentence — write "top up" there (lowercase). The casing is
matched to the rendering context.

**Inconsistent casing is a bug.** If you see mixed cases, it's
because the rendering context is wrong, not because the ARB is
malformed.

### "Top Up" / "top up" / "TOP UP" spelling

Always:
- Title case (button labels, screen titles): **Top Up**.
- Sentence / in-sentence (body text): **top up**.
- ALL-CAPS labels (overline typography): **TOP UP**.

Do **not** use "Top-Up" (hyphenated) or "TopUp" (concatenated).
Hindi is "टॉप अप" (with space) for all three cases.

### No duplicate keys

JSON silently keeps the last value on duplicate keys. The previous
duplicate (lost the first definition, kept the second) is a
footgun. Don't introduce duplicates.

To check for duplicates in a fresh ARB, run:

```bash
cd flutter
dart run tools/find_truly_unused_arb.dart | head -1
# (also flags dead keys; the dead-keys count includes duplicates
# that the stripper would have caught.)
```

If the count is unexpectedly high, inspect the report before
deleting — the script may have false positives.

### No `?? 'English fallback'` for L10n calls

Every L10n call should use the key. The fallback hides missing
translations from CI. Use the key directly and let the app crash
loudly if the ARB is missing the entry — that's a build-time fix,
not a runtime band-aid.

```dart
// Wrong:
Text(AppLocalizations.of(context)?.txtwelcome ?? 'Welcome'),

// Right:
Text(AppLocalizations.of(context)!.txtwelcome),
```

Exception: legacy migration code that predates the ARB. Mark
those with a `// TODO(i18n):` and a ticket.

### When to add a new key vs reuse

Add a new key when:
- The string is a user-facing label.
- The value is unique to the screen.
- Reusing a similar key would force the screen to display
  contextually wrong text.

Reuse an existing key when:
- The text is genuinely identical across screens.
- The semantic meaning is the same (e.g. "Save" button across
  forms).

When in doubt, add a new key. ARB-key inflation is cheaper than
display-text regression.

## ARB file editing

### Use Python with explicit bytes I/O, not PowerShell

On Windows, PowerShell `Set-Content` adds UTF-8 BOM and CRLF, both
of which the Flutter `gen-l10n` parser rejects with a misleading
"unexpected character" error. Always use Python:

```python
from pathlib import Path
p = Path("flutter/lib/l10n/app_en.arb")
raw = p.read_bytes()
text = raw.decode("utf-8")
# ... edit text ...
p.write_bytes(text.encode("utf-8"))
```

After editing, validate the JSON:

```bash
python -c "import json; json.load(open('flutter/lib/l10n/app_en.arb', encoding='utf-8-sig'))"
```

### After editing, regenerate and run tests

```bash
cd flutter
flutter gen-l10n
flutter analyze
flutter test
```

## The 7 form-widget unique keys

`lib/widgets/forms/voltium_phone_field.dart` derives the following
two keys from `fieldKey`:

- `sendOtpButton` → `'${fieldKey?.value ?? 'phone'}_sendOtpButton'`
- `verifyOtpButton` → `'${fieldKey?.value ?? 'phone'}_verifyOtpButton'`

When two `VoltiumPhoneField` instances sit on the same screen (e.g.
rider phone + guarantor phone in the guarantor onboarding flow),
each has a unique key. Tests should assert against the derived
key, not the constant.

The legacy `Key('sendOtpButton')` in
`flutter/lib/features/auth/presentation/widgets/otp_trigger_widget.dart`
is a separate widget. Its tests pass unchanged because the new
derivation only affects the Voltium form widgets.

See `flutter/docs/form-widgets.md` for the full form-widget
contract.
